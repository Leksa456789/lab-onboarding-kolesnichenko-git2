2. Цели ревью

2. Убедиться в функциональной корректности сценариев входа, 2FA и жизненного цикла токенов (выпуск, продление, отзыв) до релиза через 2 недели.
3. Проверить устойчивость и сопровождаемость кода критичного модуля: нет магических чисел, секретов в коде, понятная структура для будущих разработчиков.

3. Критерии проверки (чек-лист)

3.1. Функциональная корректность
- [ ] Покрытие тестами модуля авторизации не ниже 90% (строки и ветки)
- [ ] Тесты есть для всех сценариев: успешный вход, неверный пароль, блокировка, ввод кода 2FA, истёкший и отозванный токен
- [ ] Access-токен живёт не дольше 15 минут, refresh-токен отзывается при выходе из системы

3.2. Безопасность / Надежность
- [ ] Пароли хранятся только в виде хеша (Argon2 или bcrypt), открытых паролей нет ни в коде, ни в БД
- [ ] После 5 неудачных попыток входа учётная запись блокируется, на эндпоинт входа действует rate limit
- [ ] Код 2FA одноразовый, срок действия не более 5 минут
- [ ] В логах и ответах API 0 паролей, токенов и персональных данных в открытом виде
- [ ] 0 секретов (ключей, паролей) в коде и истории PR по результатам gitleaks
- [ ] 0 уязвимостей уровня Critical и High по результатам SAST (bandit)
- [ ] Персональные данные передаются только по TLS и хранятся в соответствии с 152-ФЗ

3.3. Производительность
- [ ] Время ответа эндпоинта входа не более 300 мс (p95) при 100 запросах в секунду
- [ ] Не более 3 запросов к БД на один вход (нет N+1)

3.4. Читаемость и стиль
- [ ] flake8 без замечаний, форматирование соответствует .editorconfig
- [ ] Функции не длиннее 40 строк, у публичных функций есть docstring
- [ ] Магические числа вынесены в именованные константы или настройки
